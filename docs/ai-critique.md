# AI critique of the M1 infrastructure

|#|Severity|Finding|Why it matters|Suggested fix|
|-|-|-|-|-|
|1|High|Private subnets have no way out: no NAT Gateway and no VPC endpoints.|M2 shards cannot download packages, pull images, send logs or use SSM.|S3 gateway endpoint (free), packages baked into the image or delivered via S3, optionally one temporary NAT.|
|2|High|Role trust policy is too broad: Principal is the account root, so any identity in the account allowed to call sts:AssumeRole can use the role.|Breaks least privilege.|Name the specific user or role that may assume it, optionally with a condition.|
|3|Medium|"Read-only" is not strictly read-only: Get\* and List\* include sensitive reads (ec2:GetPasswordData, lambda:GetFunction, logs:GetLogEvents). The Deny list covers only 6 services.|A viewer could read secrets; unlisted services have no Deny guardrail.|List the exact actions needed or build on ViewOnlyAccess/SecurityAudit, and Deny sensitive reads explicitly.|
|4|Medium|Hardcoded names (kv-readonly, kv-readonly-role) and CIDRs in the templates.|A second deployment in the same account fails with AlreadyExists; the network is not reusable.|Let CloudFormation generate names; make CIDRs template parameters.|
|5|Medium|No protection against accidental deletion of kv-network.|After M2, deleting the network takes the servers' connectivity down.|Enable termination protection (update-termination-protection); disable it only for planned teardowns.|
|6|Medium|No cost guard: nothing alerts or cleans up if kv-app is left running.|A forgotten stack costs \~$28.6/month, over half of the $50 credit. AWS Budgets may be blocked in the sandbox (not tested).|Tag resources (Project=kv), add a down script that deletes kv-app, check "Used $X of $Y" at the start and end of each session.|
|7|Low|Recreatability is proven only for the network, and only through hand-typed commands.|M2 CI/CD needs this automated; manual steps invite mistakes.|One script for deploy, verify and teardown, reused by the M2 pipeline.|

## Status

- #4 fixed: IAM names are generated by CloudFormation; network CIDRs are template parameters; export names are built from the stack name, so a second deployment does not collide.

## M2: sharding (kv-app)

|#|Severity|Finding|Why it matters|Suggested fix|
|-|-|-|-|-|
|1|High|The API has no authentication, and `POST /shards` accepts any caller.|Anyone who reaches port 8080 can write data or register a rogue shard that receives keys.|Require an API key or signed requests, and restrict registration to internal callers.|
|2|High|Adding a shard does not move existing keys, so keys that now hash to the new shard return 404.|Data becomes unreachable silently after a scale-out.|Migrate keys when a shard joins (M3 rebalancing), or keep the old ring until the move finishes.|
|3|High|Tables and shard registrations exist only in memory on the coordinator and the shards.|A restart of any server loses its data and routing. Rebooting a shard loses its items.|Persist items and metadata outside the process (EBS, DynamoDB or S3), and re-register shards from configuration on boot.|
|4|Medium|The coordinator's security group allows `0.0.0.0/0` on port 8080.|The API is reachable from the whole internet with no rate limit.|Limit the ingress CIDR to your own IP during tests. Add a load balancer and auth before real use.|
|5|Medium|`HEAD` returns `Content-Length: 0` on the coordinator, while `GET` reports the real length.|Clients that size buffers from `HEAD` get the wrong value, which breaks the HTTP rule for `HEAD`. Found by the curl check in `docs/m2-curl-evidence.md`.|Forward the shard's `Content-Length` on `HEAD`.|
|6|Medium|An in-place stack update (stop, change user data, start) keeps the instance and skips the new user data, because cloud-init runs user data once per instance.|After the redeploy, the coordinator and shards kept running without the app. Nothing reported it, and the deploy reported success.|Make the instance name or a version tag part of the resource so an update replaces it. CI checks the running version through `/health`.|
|7|Medium|Shard logging is off (`log_message` returns at once), and the shards cannot be reached through SSM.|Diagnosis needs `curl` from the coordinator or the EC2 console log.|Log to stderr so systemd records it in the journal, and add a version field to `/health`.|
|8|Low|Tables cannot be deleted, and the API cannot list them.|A table cannot be removed once created.|Add `DELETE /tables/{t}` and `GET /tables` (M3 scope).|

## Status (M2)

- Open: all eight findings. #1, #2 and #3 are the scope of M3 and the CI step. #5 and #8 are small and can be fixed in the next code change.
